# Design

## Context

See proposal.md. Established facts: (1) the inventory describes only cards the user owns - zero-owned cards (the ones matching needs) get their market hashes from the badge-detail API, which is why upstream 6.0.0.12 and our port kept the detail crawl; (2) the parallel crawl shipped in 1.0.12 issues parallel Steam requests, which the user considers a ban risk; (3) the user's dataset (`data/card_counts.json`, 1,884 games, exported from the steam-cards-bot `card_counts` table) provides set sizes locally, and the user can enrich it with per-card market hashes - the bot's inventory cache accumulates exactly those hashes as it stocks complete sets. steam-cards-bot's Node code cannot be imported into the userscript (different runtime), so the integration is the exported JSON dataset, regenerated by the bot and committed here.

## Goals / Non-Goals

**Goals:**

- Zero parallel Steam requests: the badge-detail stage returns to strictly serial, web-limiter-paced fetches.
- Covered games (card list in the dataset) skip the badge-detail stage entirely: card slots derive from the dataset + inventory counts.
- Set sizes resolve locally first; the remote badges database becomes a lazy fallback for uncovered games.
- Graceful degradation: every dataset level (counts-only, sizes+names, sizes+card lists) works, with the serial crawl as the final fallback.

**Non-Goals:**

- Importing steam-cards-bot code/libraries into the userscript (runtime mismatch); the integration is the exported JSON.
- Bundling per-card data the user cannot generate yet - the schema supports card lists, but counts-only data works today.
- Changing matching, fairness, balance, owned-vs-tradable semantics, scan filters, settings, or the trade-offer flow.

## Decisions

### D0: Learned badge card data persists in the browser

A game's card data is static (a set's composition never changes), so the scanner treats it as learn-once information. One new versioned storage key (`TempAsfStm.ASF.STM.BadgeCards.v1`, single JSON document via the existing storage lib) holds a map of appId -> `{size, name?, cards: [{hash, title}]}` in the order the badge-detail API reported (canonical slot order). Resolution order per game: bundled dataset -> browser cache -> serial badge-detail fetch (which writes the cache). The cache is read once per scan, written incrementally as games are learned, and bounded in practice (~300-500 B per game; hundreds of games fit far below the ~5 MB localStorage budget). A versioned key plus the existing readJson corruption fallback means a bad cache is ignored, never fatal.

- Why a single document instead of per-game keys: one read/write per scan matches the existing settings-store pattern and keeps the storage-lib surface unchanged.
- Other localStorage candidates audited: bot list (already cached with TTL), trade params and blacklist (already persisted), inventory counts and bot badge pages (must stay fresh - excluded deliberately); badge levels/titles for the USER are static per game and ride along in the same cache.

### D1: Dataset schema (two levels, one file)

`data/card_counts.json` is normalized to:

```json
{
  "<appid>": {
    "size": 5,
    "name": "Game Title",
    "cards": ["<exact market_hash_name>", "<exact market_hash_name>"]
  }
}
```

- `size` (required): set size - today's `card_count` value; drives eligibility without any request.
- `name` (optional): badge display name; when absent for a covered game, the badge title falls back to `AppID <appid>` (recorded trade-off; adding names later fixes the display without code changes).
- `cards` (optional): the exact `market_hash_name` of every card in the set - unlocks the covered-game fast path (no badge-detail request). Must be the exact Steam string: the offer page resolves bot items by exact hash, and the existing missing-items abort catches wrong hashes.

The dataset loader normalizes the current counts-only export (`[{"app_id","card_count"}]`) into this shape, so implementation lands before the user enriches the data.

### D2: Build-time bundling

rolldown inlines the dataset (same template-text mechanism as the CSS import) - the userscript carries it; no runtime fetch, no raw.githubusercontent dependency for covered games. The current 70 KB counts-only file shrinks to ~25 KB minified (short-value numbers, no repeated keys); with card lists the dataset grows to roughly 400-600 KB - acceptable for a userscript and compressible later by splitting the hash into a shared game prefix if ever needed.

### D3: Covered-game derivation replaces the detail fetch; title-based partner mapping

When a candidate game's card list is known (bundled dataset or browser cache), card slots are built as hash -> `{owned, tradable}` from the counting pass (owned copies only; the fail-open tradability rule applies), plus a zero-count slot for every known hash with no inventory copy (receive-side slots - the blocker that forced the badge API before). The bundle/cache provides hashes for ALL set slots including zero-owned ones, which is exactly what made the badge-detail API load-bearing before.

Partner mapping goes **title-based uniformly** (no dependency on Steam's badge-page slot order): each partner page card title is matched against the user's card titles/market hashes - exact match first, then suffix match (card market hashes embed the card name after the game prefix) - and an unmatchable partner card skips the whole badge with a debug note. To keep titles comparable across locales, every Steam text fetch involved (`ajaxgetbadgeinfo`, partner badge pages) is pinned to `l=english`. Dataset-game cards display their market hash as the title (cosmetic asymmetry; per-card titles can be added to the dataset later).

### D4: Serial fallback for everything else

Games with no known card list keep the pre-1.0.12 detail fetch: one `ajaxgetbadgeinfo` at a time, web-limiter delay between requests, retry within the global error budget, invalid badges filtered, and the learned result written to the browser cache. The 1.0.12 parallel machinery (worker pool, cursor, settle counting) is removed. `processFilters` keeps working for filter-mode stubs under the same rules.

### D5: Lazy remote badges database

The remote badges-DB fetch moves behind a need check: it runs only when at least one candidate game lacks a known set size (bundle, cache) - and then provides sizes and titles for uncovered games in that run, writing them to the cache. Covered-only scans issue zero database requests; covered games without a display name show `AppID <appid>` as their title (dataset `name` field or a learned title fixes this without code changes).

## Risks / Trade-offs

- [Wrong/missing hashes in a user-supplied card list] -> Mitigation: exact strings required by schema; the offer page's existing missing-items abort catches mismatches; a size-vs-cards-count mismatch skips the badge with a debug note.
- [Dataset staleness: new games not yet in the dataset] -> Mitigation: lazy remote-DB fallback and serial detail crawl keep them working; the dataset is regenerated from steam-cards-bot on the user's schedule.
- [Userscript size growth once card lists are bundled] -> Mitigation: ~0.5 MB is well within userscript norms; hash-prefix splitting is available later if needed.
- [Covered-only scans show AppID titles until names are added] -> Mitigation: dataset `name` field; the user curates the game list.
- [Removing parallelism slows uncovered-game scans back to pre-1.0.12 speed] -> Mitigation: accepted explicitly (ban safety outweighs); the dataset shrinks the uncovered set over time.

## Migration Plan

1. Land the code change (dataset module, derivation, serial fallback, lazy remote DB, tests) in one commit; bump the package version (patch minimum) per repo rules.
2. No storage or settings migration; the dataset file is committed and regenerated from steam-cards-bot as needed.
3. Rollback: revert the commit - the parallel crawl returns (not recommended given the ban concern).

## Open Questions

None. The dataset schema answers the user's per-card question (yes - card lists are what unlock the fast path); counts-only data works today and the enriched levels activate without further code changes.
